# 11e: Database for my app

GitHub Pages only hosts **static files** (HTML, CSS, JavaScript). It cannot run
server-side code or host a database. So the database has to live somewhere else,
and my website talks to it over the internet. There are two main ways to do this:

### Option 1: Use Services
Services like **Supabase** (PostgreSQL) or **Firebase** (Firestore) provide a
hosted database and an API. The JavaScript on my page connects to it directly
using `fetch()` or the provider's SDK.

- Pros: no server to maintain, free tier available, fast to set up
- Cons: dependency on a third party, limits on the free tier

### Option 2: Own backend with a database
I build my own API (for example with Node.js, Python or PHP) and connect it to a
database such as PostgreSQL or MySQL. The backend runs on a server or a cloud
service (e.g. Render, Railway, Azure). The website on GitHub Pages calls this API:

    Browser (GitHub Pages) --fetch()--> API (backend) --> Database

- Pros: full control over logic, security and data
- Cons: more work, I need to host and maintain it

### Security
- Never put database passwords or secret keys in the frontend code, because
  everyone can read it in the browser.
- Only the backend should hold the credentials. With BaaS, use the public
  (anon) key together with access rules (e.g. Row Level Security in Supabase).
- The API must be allowed to be called from my GitHub Pages domain (CORS).

## My choice
For a small project I would use **Supabase**, because it needs no own server and
works directly from a static page. For a bigger app I would build my own API
with a database, so I have full control.
